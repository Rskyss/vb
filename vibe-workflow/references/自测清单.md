# 自测清单 —— "全绿"的具体定义

宣布"做完了"之前逐项核对。任何一项没做或没过，都不能说"做完了"。

## 一、自动化测试

- [ ] 全量测试套件通过（不是只跑新增的那几个）
- [ ] 新功能有配套测试：正常流程、边界条件、出错情况
- [ ] 项目没有测试体系？先给本次改动建立最小测试，并在台账里声明现状

## 二、真实环境走流程（核心，不可用测试替代）

- [ ] 在真实运行的应用里，像用户一样把功能完整走一遍
- [ ] 用真实数据（或逼真数据），不用 "test/111/aaa" 式的敷衍数据
- [ ] 涉及多角色/多权限的，每种身份各走一遍（如：游客、普通用户、管理员）
- [ ] 涉及权限的，验证"不该能做的人确实做不了"（权限矩阵），不只验证"该能做的人能做"
- [ ] 亲眼看到正确结果（界面渲染、数据落库、文件生成），而不是"没报错"

## 三、影响面检查

- [ ] 改动波及的原有功能抽查一遍，没被改坏
- [ ] 界面改动：亮色/暗色、不同窗口宽度看一眼（如适用）
- [ ] 数据结构变更：老数据兼容吗？升级路径验证过吗？

## 四、清理与还原

- [ ] 自测产生的测试账号、测试数据、临时配置，全部删除还原
- [ ] 在报告里明确说"已清理"，列出清理了什么
- [ ] 临时改过的配置文件（.env 等）恢复原样并复核

## 五、批量核查数据时：判据必须先验准，再信结论

用脚本/正则批量检查一批数据有没有问题时（"线上多少份报告数字算错了"这类），**判据本身就是被测对象，先验它准不准，再拿它的结论下判断**。粗判据既会漏报也会误报，而你会拿着错误统计去汇报、去决定要不要动数据。

真实案例：核查一批报告"百分比分母是否写错"，判据改了三版才准——
- 第一版只认一种固定句式 → **漏掉 6 份**，误报"只有 14 份有问题"
- 第二版把所有百分比都算进来 → 把"工程进度 60.66%"这种无关数字也当成问题，**误判正确的报告为错**
- 第三版只认真正的立场占比数值、且看上下文里能否找到正确分母 → 才对

- [ ] 判据在**已知正确**的样本上跑一遍，确认不误报
- [ ] 判据在**已知有问题**的样本上跑一遍，确认不漏报
- [ ] 抽 3–5 条命中结果**人工逐条读**，确认真是问题（不是判据自己臆造的）
- [ ] 报告数字时说清判据是什么，别只给"X 份有问题"这个光秃秃的数

同理适用于修复效果验收：**修完再用同一套判据复测**，别默认"改了代码就一定好了"——那次修完重跑，13 份里仍有 1 份没修好，正是复测才发现的。

## 六、如实报告

报告格式：结论 + 证据。

- 每项自测写清：测了什么 → 怎么测的 → 看到了什么结果
- 失败的、跳过的、没把握的，如实写，不粉饰
- **绝对禁止**：把"应该没问题"说成"验证通过"；把残缺状态报成"已完成"

> 真实案例：一次进程崩溃后，残缺的任务被含糊报成"已完成"，用户基于假信息做了后续决策。诚实的坏消息永远好过体面的假消息。
