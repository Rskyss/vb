# 版本与推送规则

## 基本认知

用户不读 commit，靠**版本号和 Release 说明**感知产品进度。commit 是施工日志（给开发/AI 看），版本是里程碑（给用户看），两者不是一回事。

## 版本号：三段制 `v 大版本 . 功能版 . 修复号`

| 段位 | 管什么 | 什么时候 +1 |
|---|---|---|
| 第一段 大版本 | 产品阶段 | 只动一次：**产品正式对外上线那天 0 → 1**（条件见下） |
| 第二段 功能版 | 新能力 | 这次**让用户多了一件能做的事** |
| 第三段 修复号 | 修补 | 这次**没让用户多出能做的事**（修复／收尾／优化／加固） |

**判断顺序（照此三问，别凭感觉）：**

1. 今天正式对外上线了？→ `v1.0`（后两段归零）
2. 能用一句"现在你可以……了"说出来？→ 第二段 +1，**第三段归零**（`v0.91.2` → `v0.92`，不是 `v0.92.2`）
3. 都不是 → 第三段 +1（`v0.92` → `v0.92.1`）

**配套细则：**

- **前面的位一动，后面的位全部归零**；第三段为 0 时不写出来（写 `v0.92`，不写 `v0.92.0`）
- **第三段不要求与上一版是"同一个功能"**：判断只看"有没有新增能做的事"，无关功能的独立修复照样走第三段，在正文第一行写明它修的是什么
- **修订号只用数字，禁止字母**：`v0.91.a` 在业界表示"发布**前**的 alpha 测试版"，与"发布**后**的补丁"含义正好相反，且会打乱标签排序
- **不跳号、不倒退**，每次只 +1；上一版有问题也不改号，出新版修
- **走到 `v0.99` 时**：不要续成 `v0.100`（技术上合法，但会被误读成比 `v0.99` 小）。此时若已满足下方 1.0 条件就顺势切 `v1.0`；不满足则先补条件，别硬发版
- **什么时候该发版**：台账里一个顶层任务首次被用户验收通过时。同一任务下追加的小要点不单独打版本，除非用户主动说"这个也算一版"
- 分量介于"小更新"和"大功能"之间、拿不准算不算一版：**问用户**，不要自行判断

## 切 `v1.0` 的条件

**1.0 不是"功能够多了"，是"我敢对外承诺了"。** 判断标准：*一个陌生人付了钱或投入了真实工作在这上面，出了问题兜得住吗？*

必须全部满足：

1. **核心链路稳定**——成功率有数字（如"30 场重跑 30/0"），不是"感觉挺稳"
2. **失败不会骗人**——出错提示的原因是对的，不会把排查带偏
3. **数据不会丢**——有自动备份**且演练过恢复**
4. **出事你能知道**——关键故障有告警，不靠用户来报
5. **能回滚**——发版出问题几分钟内退回上一版
6. **隐私承诺兑现**——说删就真删（含云端）

若 1.0 起开始收费，另加：付费链路完整（能付／能凭证／能退）、额度计费准确且用户可自查、有基本服务说明。

**不该拦住 1.0 的**：功能不必齐全、界面不必完美、性能不必最优——1.0 承诺的是质量，不是数量。

**建议的触发信号**：*连续两三周，线上所有问题都是自己先发现的，而不是用户告诉你的。* 这一条直接证明了第 4 条，而那正是 1.0 承诺的核心。

## 推送铁律：一个版本＝远端恰好一个提交

本地开发期照常小步提交（这有利于回退），**推送前合并成唯一一个提交**：

```bash
git reset --soft origin/main   # 把本地所有未推送提交退回暂存区
git commit -m "vX.Y 一句话主题

新增功能：
- xxx（用产品语言）

优化功能：
- xxx

修复bug：
- xxx"
```

- 标题必须短：`vX.Y 一句话主题`（十几个字），不堆要点
- 明细全部放正文，按固定三组分类（没有的组省略）
- **为什么**：真实案例——某版本推送后又陆续补了一串零碎 docs 提交，远端历史变成流水账，用户翻版本时完全看不出哪次是一版，最终只能改写历史收拾，代价远大于当初一次做对

## 不发版＝不推主干（这个空子被钻过两次）

上面只规定了"发版时怎么推"，**没规定"不发版时能不能推"**。这个空白被钻过两次：用户说"这个改动不单独发版"，AI 理解成"不打版本号、但可以单独推一个提交上去"，于是往主干推了 `fix:` / `docs:` 开头的零碎提交——两次都是用户事后翻 commit 列表才发现，两次都只能改写历史收拾。

**明确规定：**

- 改了但还没到发版时机 → **本地提交攒着，不推主干**
- 用户说"不单独发版"＝这些改动等下次发版时**并进那一个 `vX.Y` 提交**，**不是**"可以单独推一个非版本提交"
- 主干上只允许 `vX.Y 一句话主题` 格式的提交，没有豁免类别（`docs:` `fix:` `chore:` 一律不行）

**需要跑 CI 验证怎么办**——第二次被钻正是这个需求逼的：CI 只在推送时触发，AI 为了验证修复有效只好推主干。正道是推临时分支：

```bash
git push origin HEAD:ci-check-xxx        # CI 照跑，主干保持干净
git push origin --delete ci-check-xxx    # 验证完删掉
```

**装机械拦截，别靠自觉**——文档挡不住理解偏差（两次都是读着同一份规则犯的）。把本 skill 的 `assets/pre-push` 拷进项目并启用：

```bash
mkdir -p .githooks && cp <skill目录>/assets/pre-push .githooks/ && chmod +x .githooks/pre-push
git config core.hooksPath .githooks      # 本机配置：换机器或重新 clone 后要再执行一次
```

它会拒绝一切标题不以 `vX.Y ` 开头的提交推向主干，并打印该怎么做。确属例外须经用户明确同意才可用 `--no-verify` 绕过。

## 推送前收尾清单（全部做完才允许 squash）

- [ ] 全量测试绿
- [ ] 台账登记完成、状态已更新
- [ ] 验收记录写完
- [ ] 版本记录列表加了这一版
- [ ] 界面上显示版本号的地方（页脚等）已更新
- [ ] 正确顺序：改代码 → 测试绿 → 台账全登记 → squash → push → tag → Release

## 对外动作必须请示

推送、打 tag、创建 Release——每一次都先问用户"要不要现在做"，得到明确指令才执行。规则本身不能替代这次询问。改写历史类操作（squash 已推送的提交、重指 tag）只在用户明确指令下做。

## Release 说明

- 用 tag 说明创建 Release，内容摘自台账对应条目
- 用产品语言：用户读完知道"这版我能感知到什么变化"，而不是一串技术名词
